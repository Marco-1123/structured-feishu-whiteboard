# Quality Checklist

生成飞书画板前后都要检查。不要只依赖命令成功。

## 信息质量

- 容量、指标和占位符判断以 `content-budget.md` 为准；本清单只做最终核对。
- 标题是否直接说明主题或结论。
- 是否有一个明确主结论。
- 是否只保留 3 到 6 个关键模块。
- 每个模块是否有独立信息价值。
- 是否删除了重复、铺垫和过程性说明。
- 是否避免把“用户让我整理”“来源是某文档”“使用某风格”等元信息写到画板上。
- 是否按 `content-budget.md` 判断了短内容、中等内容、长文或复杂材料。
- 长文是否先形成信息保全清单，再组织成顶部总览和同页后续区域，而不是把全文搬上画板。
- 是否清理了乱码、异常符号、长 URL、脚注和格式残片。
- 指标是否符合 `content-budget.md`：有业务语义、没有同类重复、呈现层级唯一。
- 指标区是否统一对齐：同宽、同基线、同字号、同间距。
- 单张画板是否只承载一个主表达任务；总览、指标、路线、对比是否被混在一起。

## 结构质量

- 版式是否符合内容关系。
- 阅读顺序是否明显。
- 重要信息是否在视觉上更突出。
- 同级模块是否尺寸和层级一致。
- 对比矩阵是否维度清楚。
- 路线图和流程图是否方向明确。
- 内容是否超过所选版式的容量边界。
- 如果内容超载，是否压缩或拆图，而不是缩小字号硬塞。
- 主结论是否位于主视觉区，而不是右上角补丁式小框。
- 并列模块是否误用了箭头；只有推进、流程或依赖关系才使用箭头。

## 视觉质量

- 颜色是否只使用选定风格库。
- 强调色是否克制。
- 卡片边距、行距和安全边距是否充足。
- 同一容器内的上下留白是否均衡；标题、正文、标签不能整体偏上或偏下。
- 卡片底部标签、按钮或徽标是否离底边至少保留一行文字高度的安全距离。
- 字号层级是否清楚。
- 是否存在无意义装饰。
- 是否避免过多边框、阴影和标签。
- 是否存在三层以上框套框；同一区域最多两层容器。
- 卡片内是否同时堆了动作列表、多个指标框和读法说明；如有，必须拆分。
- 是否存在上下两个指标层导致视觉重复和不对齐。
- 底部说明条是否抢走主内容注意力；专业蓝白风默认不用大面积黑色说明条。
- 箭头是否连接了明确对象；不能压住文字，也不能漂浮在两段文字之间造成读向歧义。
- 长文是否通过同页区域扩展增加容量，而不是生成难读的单个长竖图或切成多个页面。

## 画板产物质量

- 生产交付必须由 `scripts/render-whiteboard.mjs`、`scripts/render-whiteboard-dsl.mjs` 或明确试点的 `scripts/render-whiteboard-v4.mjs` 生成；除非用户明确接受实验性手写 SVG。
- 如果内容被判断为路线图、流程、价值链、对比矩阵、时间线、漏斗、金字塔或指标看板，必须使用对应脚本化模板，不能自由手写整图。
- SVG 产物正文使用 `<text>` / `<tspan>`。
- DSL 产物必须由白板节点组成，不能退化为整张截图。

## SVG 兼容质量

- 正文使用 `<text>` / `<tspan>`。
- 主体结构使用 rect、circle、ellipse、line、polyline。
- 没有 gradient、filter、pattern、clipPath、mask。
- 没有透明度属性。
- 没有手绘箭头头部。
- `<path>` 只出现在 marker 里。
- 长文本已拆成明确 `<tspan>` 行，不依赖自动换行。

## 渲染检查

运行：

```bash
npx -y @larksuite/whiteboard-cli@^0.2.11 -i diagram.svg -o diagram.png -f svg
npx -y @larksuite/whiteboard-cli@^0.2.11 -i diagram.svg -f svg --check
node scripts/check-svg-layout.mjs diagram.svg
grep -nE '<polygon|opacity=|fill-opacity=|stroke-opacity=|<filter|<linearGradient|<radialGradient|<clipPath|<mask' diagram.svg
```

如果是 V4 SVG 试点产物，额外运行：

```bash
node scripts/check-v4-layout.mjs diagram.svg
```

V4.3 产物还必须运行：

```bash
node scripts/check-v43-visual-quality.mjs diagram.svg
```

该检查读取顶层布局标记，验证区域重叠、列高差、底部安全距离、画布比例、有效内容占比、稀疏模块过度拉伸和连续全宽积木墙。它不能替代飞书侧预览，但可以挡住工具合法、视觉明显失衡的产物。

并确认 SVG 含有 `data-layout-engine="v4"`，否则说明没有走 V4 并行布局引擎。

如果是 V3.2 DSL 产物，运行：

```bash
npx -y @larksuite/whiteboard-cli@^0.2.11 -i diagram.json -o diagram.png
npx -y @larksuite/whiteboard-cli@^0.2.11 -i diagram.json --check
```

必须人工查看渲染图，重点检查：

- 文字是否溢出卡片。
- 模块是否互相重叠。
- 内容是否被画布裁切。
- 卡片是否太挤。
- 卡片内上下留白是否视觉均衡。
- 箭头是否与步骤、阶段或流程节点对齐。
- 主结论是否足够醒目。
- 是否出现乱码、控制字符、未转义符号或原文格式残片。
- 是否存在“看似没溢出但整体过密”的拥挤问题。
- 是否存在容器过密、边框过多导致的“框套框”观感。
- 子元素是否越过父容器边界；白板工具可能不会稳定发现这类问题，必须用本地布局检查和人工预览同时确认。
- V4/V4.2 产物是否避免“高密度内容小窄框化”：长说明不得被硬塞进过窄列。
- V4.3 beta.2 产物是否避免相反问题：四到六个短并列项不能因为条目数量被拉成连续全宽长条，应优先共享行或使用两列内部网格。
- V4.3 产物的同排模块高度差是否不超过 32px，避免短模块下方形成没有语义的空洞？
- V4.4 expression-canvas 是否保持真正的一览图比例？默认宽高比不得低于 1.1，推荐 1.3 到 1.8；低于门槛视为纵向报告条，不得交付。
- 规划器选出的 `pageSkeleton` 是否出现在最终 brief 和 SVG 根节点中，并实际改变模块组合？
- 材料存在明确数字、单位、比例、上下界时，是否至少形成一组指标卡或数据组件，而不是全部写进证据列表？
- 是否连续出现三个以上同构文字列表？如有，必须重新分配为指标、状态、方向链、比较或行动组件。
- 是否存在为了凑模块数量生成的“补充信息”或重复事实？如有，删除该模块并重新组合剩余区域。
- 流程与能力是否分层表达？流程节点不能被塞进普通能力状态板，能力标签也不能冒充流程步骤。
- 风险是否使用风险簇、证据是否使用编号证据卡、行动是否使用行动清单，而不是三者共用同一种竖色条列表？
- 用户可见文案是否只表达业务内容，不包含“适合两列”“不需要占满整行”“回归样例”等测试或排版说明？
- 流程图连线是否先于节点绘制，起终点是否连接节点边界，且不穿越无关节点？
- 4 到 6 个简短线性步骤是否保持单一阅读方向，避免机械换行产生跨画布回路线？
- V4/V4.2 指标卡是否给数值、说明和状态标签分别留出空间，不能让标签压住说明。
- V4/V4.2 流程节点是否足够宽；有正文的节点不能为了横向一排而退化成多个窄卡片。
- V4 检查器通过后仍要人工判断是否落入两个极端：很多小窄框，或很多稀疏全宽长条。前者应增加跨度，后者应缩小跨度并组合网格。

发现局部问题时，直接小范围修改 brief 或对应渲染器：移动、加宽、换行、增高、删减低价值文字。不要为了一个局部问题自由重写整张图。

如果局部修改仍需要降低到字号底线以下，按 `overflow-repair.md` 拆图。

## 交付检查

交付前确认：

- 飞书文档链接可用。
- 画板内容已写入，不是空白。
- 返回了预览图。
- V4.3 返回了 `run-manifest.json`，并且 critical coverage 与 high accounting 都为 100%。
- 回复中说明采用的版式和风格。
- 回复中说明必要的信息压缩，但不冗长解释制作过程。
